## 0. Infrastructure (Phase 1)

**Persistence:** PostgreSQL 16 via Docker (not SQLite). SQLAlchemy 2.0 async (`asyncpg` driver) + Alembic for migrations.

**Why Postgres over SQLite:** the assignment explicitly asks for a `docker-compose` setup and JSON columns for flexible fields (constraints, steps, output). Postgres's native `JSON` type plus a real migration history (Alembic) demonstrates the same operational discipline as a production system, at negligible extra setup cost given Docker is already required. SQLite would have been the faster path but would have meant no separate `db` service to actually containerize. Also better for future plans for the app.

**Migrations, not `create_all()`:** the initial schema (4 tables: `tasks`, `execution_plans`, `execution_steps`, `agents`) is generated via `alembic revision --autogenerate` from the SQLAlchemy models — never hand-typed `op.create_table` calls. The 4 agent rows are seeded by a second, separate migration, since seed data can't be autogenerated from a model diff; that one is legitimately hand-written. This means a fresh database is immediately usable after one `alembic upgrade head`, and every future schema change follows the same pattern: change the model, run autogenerate, review the diff, commit.

**Config: atomic values in `.env`, computed in `Settings`:** `.env` holds only atomic pieces (`POSTGRES_HOST`, `POSTGRES_USER`, `APP_PORT`, ...), never a pre-built connection string. `app/config.py`'s `Settings.database_url` is a computed property built from those pieces, and `docker-compose.yml` reads the same `POSTGRES_*` variables for the `db` service's credentials. Earlier, `DATABASE_URL` was typed three times (`.env`, a hardcoded override in `docker-compose.yml`, and a default in `config.py`) — a value only one of those three actually drove, since compose's `environment:` block silently overrode whatever `.env` had. Decomposing into parts removes the duplication entirely: there's exactly one place each credential is typed.

**Dev/prod Docker split:** `Dockerfile.dev` (editable install, dev extras, `--reload`, source bind-mounted) and `Dockerfile.prod` (frozen install, runtime deps only, no reload, self-contained image) are separate files, chosen by `.env`'s `APP_ENV` via `dockerfile: Dockerfile.${APP_ENV}` in `docker-compose.yml`. One Dockerfile trying to serve both purposes behind conditionals would be harder to read than two small, single-purpose files.

**Test config lives in `tests/`, not `app/config.py`:** the test database name used to be a field on the production `Settings` model (`test_database_url`), even though nothing under `app/` ever read it. Moved to `tests/settings.py`, which reuses the shared connection pieces (host, port, credentials) from `app.config.Settings` but reads the test-only database name directly from the environment — so the app's config model only ever carries fields the app itself uses.

**Data model deviation from the spec's literal schema:** the assignment's `Agent` entity lists `name` and `type` as separate fields. Here they collapse into one (`name`) — in this design there's exactly one agent instance per type, so `name` _is_ the routing key, and a separate `type` column would only duplicate it.

**`ExecutionPlan.steps` (JSON) vs. `ExecutionStep` rows:** both exist, and this looks redundant at first glance. `ExecutionPlan.steps` stores the plan exactly as the planner returned it — an immutable audit record. `ExecutionStep` rows normalize the same step definitions into queryable, mutable columns (status, output, tokens, timing) that change as execution proceeds. Keeping both means you can always diff "what the planner proposed" against "what actually happened," which matters for debugging planner quality independently of execution bugs — a real observability benefit, not duplication for its own sake.

**Bugs only found by actually running the stack (not by review):**

- `asyncpg.exceptions.InterfaceError: cannot perform operation: another operation is in progress` on every DB test. Root cause: `pyproject.toml` set `asyncio_default_fixture_loop_scope = "session"` but left `asyncio_default_test_loop_scope` at its default (`"function"`). The session-scoped `test_engine` fixture's asyncpg connections were bound to the session's event loop, but each _test_ ran in its own separate loop — crossing event loops corrupts asyncpg's connection state. Fix: set both to `"session"`, with a comment explaining why they have to match.
- Editing `pyproject.toml` had no effect inside the running container. `docker-compose.yml` bind-mounted `./app`, `./tests`, `./alembic` for live reload but not `./pyproject.toml`, so it stayed frozen at whatever was baked in at `docker build` time. Added `./pyproject.toml:/srv/pyproject.toml` to the app service's volumes.

Both were invisible to code review — they only showed up once `docker compose exec app pytest` actually ran against real Postgres, which is the whole reason this project's tests hit a real database instead of mocks.
