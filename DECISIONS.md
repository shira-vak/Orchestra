# Design Decisions

This file is filled in phase by phase, alongside the code — not written retroactively. Sections below are marked `TBD` until the relevant phase lands.

## 0. Infrastructure (Phase 1)

**Persistence:** PostgreSQL 16 via Docker (not SQLite). SQLAlchemy 2.0 async (`asyncpg` driver) + Alembic for migrations.

**Why Postgres over SQLite:** the assignment explicitly asks for a `docker-compose` setup and JSON columns for flexible fields (constraints, steps, output). Postgres's native `JSON` type plus a real migration history (Alembic) demonstrates the same operational discipline as a production system, at negligible extra setup cost given Docker is already required. SQLite would have been the faster path but would have meant no separate `db` service to actually containerize. Also better for future plans for the app.

**Migrations, not `create_all()`:** the initial schema (4 tables: `tasks`, `execution_plans`, `execution_steps`, `agents`) is generated via `alembic revision --autogenerate` from the SQLAlchemy models — never hand-typed `op.create_table` calls. The 4 agent rows are seeded by a second, separate migration, since seed data can't be autogenerated from a model diff; that one is legitimately hand-written. This means a fresh database is immediately usable after one `alembic upgrade head`, and every future schema change follows the same pattern: change the model, run autogenerate, review the diff, commit.

**Config: atomic values in `.env`, computed in `Settings`:** `.env` holds only atomic pieces (`POSTGRES_HOST`, `POSTGRES_USER`, `APP_PORT`, ...), never a pre-built connection string. `app/config.py`'s `Settings.database_url` is a computed property built from those pieces, and `docker-compose.yml` reads the same `POSTGRES_*` variables for the `db` service's credentials. Earlier, `DATABASE_URL` was typed three times (`.env`, a hardcoded override in `docker-compose.yml`, and a default in `config.py`) — a value only one of those three actually drove, since compose's `environment:` block silently overrode whatever `.env` had. Decomposing into parts removes the duplication entirely: there's exactly one place each credential is typed.

**Dev/prod Docker split:** `Dockerfile.dev` (editable install, dev extras, `--reload`, source bind-mounted) and `Dockerfile.prod` (frozen install, runtime deps only, no reload, self-contained image) are separate files, chosen by `.env`'s `APP_ENV` via `dockerfile: Dockerfile.${APP_ENV}` in `docker-compose.yml`. One Dockerfile trying to serve both purposes behind conditionals would be harder to read than two small, single-purpose files.

**Test config lives in `tests/`, not `app/config.py`:** the test database name used to be a field on the production `Settings` model (`test_database_url`), even though nothing under `app/` ever read it. Moved to `tests/settings.py`, which reuses the shared connection pieces (host, port, credentials) from `app.config.Settings` but reads the test-only database name directly from the environment — so the app's config model only ever carries fields the app itself uses.

**Data model deviation from the spec's literal schema:** the assignment's `Agent` entity lists `name` and `type` as separate fields. Here they collapse into one (`name`) — in this design there's exactly one agent instance per type, so `name` _is_ the routing key, and a separate `type` column would only duplicate it.

**`ExecutionPlan.steps` (JSON) vs. `ExecutionStep` rows:** both exist, and this looks redundant at first glance. `ExecutionPlan.steps` stores the plan exactly as the planner returned it — an immutable audit record. `ExecutionStep` rows normalize the same step definitions into queryable, mutable columns (status, output, tokens, timing) that change as execution proceeds. Keeping both means you can always diff "what the planner proposed" against "what actually happened," which matters for debugging planner quality independently of execution bugs — a real observability benefit, not duplication for its own sake.

**Bugs only found by actually running the stack (not by review):**

- `asyncpg.exceptions.InterfaceError: cannot perform operation: another operation is in progress` on every DB test. Root cause: `pyproject.toml` set `asyncio_default_fixture_loop_scope = "session"` but left `asyncio_default_test_loop_scope` at its default (`"function"`). The session-scoped `test_engine` fixture's asyncpg connections were bound to the session's event loop, but each _test_ ran in its own separate loop — crossing event loops corrupts asyncpg's connection state. Fix: set both to `"session"`, with a comment explaining why they have to match.
- Editing `pyproject.toml` had no effect inside the running container. `docker-compose.yml` bind-mounted `./app`, `./tests`, `./alembic` for live reload but not `./pyproject.toml`, so it stayed frozen at whatever was baked in at `docker build` time. Added `./pyproject.toml:/srv/pyproject.toml` to the app service's volumes.

Both were invisible to code review — they only showed up once `docker compose exec app pytest` actually ran against real Postgres, which is the whole reason this project's tests hit a real database instead of mocks.

## 1. Task Decomposition Strategy

**Approach chosen:** `Planner.decompose` (`app/planner/planner.py`) sends the goal + constraints to the LLM with a fixed system prompt (`app/planner/prompts.py`) asking for a JSON object of `{"steps": [{id, agent, action, input, dependencies}]}`. The response is parsed through the `Plan`/`PlanStep` Pydantic schemas (`app/planner/schemas/`), so a structurally malformed response (wrong types, missing fields, an agent name that isn't one of the 4 valid `AgentName` values) is rejected by Pydantic itself before any custom validation runs.

**Planner prompt:** kept deliberately minimal — the 4 agent names plus a one-line description of what each is for, the exact JSON shape expected, and an instruction to prefer fewer steps over more. No few-shot examples; the JSON shape is simple enough that Haiku produces it reliably, and few-shot examples would only inflate the prompt for a task that's really "extract structured output," not creative generation.

**Validation:** `app/planner/validation.py`'s `validate_plan` checks two things beyond what Pydantic already guarantees: every `dependencies` entry actually refers to a step id in the same plan, and the dependency graph has no cycle. Both raise `InvalidPlanError` (→ HTTP 422, see `app/main.py`'s handler). The LLM call + parse + validate round-trip retries up to `PLANNER_MAX_ATTEMPTS` (3) times before giving up — malformed JSON or an invalid graph is common enough with LLM output that one bad attempt shouldn't fail the whole task.

## 2. Dependency Management

**Approach chosen:** each `PlanStep` lists its own `dependencies` (a list of other step ids) — no separate adjacency structure. `app/execution/context.py`'s `build_step_input` looks up each dependency's already-computed output and appends it to the step's own `input` text before the step's agent ever runs, so a step naturally builds on its dependencies' results.

**Data passing:** dependency outputs are plain text, concatenated under a `### Output of <step_id>` heading per dependency. No structured/typed handoff between agents — every agent's `run` takes and effectively works with text, so this keeps the interface uniform without needing per-agent-pair adapters.

**Cycle detection:** `app/planner/validation.py`'s `_build_parallel_groups` runs a Kahn's-algorithm-style topological layering pass — repeatedly peel off every step whose dependencies are all already assigned to an earlier layer. If a pass produces no new layer while steps remain, those steps can only be waiting on each other, i.e. a cycle — so cycle detection and parallel-layer computation fall out of the exact same algorithm instead of being two separate graph walks.

---

## 3. Parallel Execution

**Approach chosen:** the parallel_groups computed by `validate_plan` (a list of layers, each layer a list of step ids with no dependency on each other) are executed layer by layer in `app/execution/engine.py`'s `ExecutionEngine.run`. Within one layer, every step's `_run_step` coroutine is scheduled together via `asyncio.gather`, so independent steps genuinely run concurrently instead of just being declared "parallel" on paper (verified by `tests/test_execution_parallel.py`, which asserts on wall-clock time, not just output correctness).

**Concurrency limit:** an `asyncio.Semaphore(MAX_CONCURRENT_LLM_CALLS)` (see `app/config.py`) wraps each step's actual LLM call, so a layer with many independent steps still caps how many LLM calls are in flight at once — bounding cost and avoiding provider rate limits — without capping how many layers can run one after another.

**Error handling:** a step that exhausts `STEP_RETRY_ATTEMPTS` retries (via `app/execution/retry.py`'s plain hand-written retry loop — no backoff library) is marked `FAILED`. Every step that transitively depends on a failed (or skipped) step is marked `SKIPPED` instead of silently running with missing context — `ExecutionEngine` tracks a `blocked` set of step ids across the whole run for exactly this. Independent steps in other branches of the graph are unaffected and still complete normally (`tests/test_error_handling.py` covers both the propagation case and the "sibling keeps going" case).

## 4. Failure Recovery

**Approach chosen:** a task reaches a terminal status via `app/tasks/task_runner.py`'s `TaskRunner._finalize`, checked in this order: **cancelled** (an explicit `POST /tasks/{id}/cancel` always wins, even over a run that happened to finish anyway), then **failed** (every step produced nothing), then **completed** (at least one step produced output — even if others failed or were skipped). Planning failures are separate and synchronous: `TaskManager.submit` awaits the planner directly, so an `InvalidPlanError` fails the *request* with 422 before a task or plan is ever persisted — see Section 1.

**Retry logic:** `STEP_RETRY_ATTEMPTS` (see `app/config.py`), applied per step by `app/execution/retry.py`'s plain retry loop — already covered in Section 3.

**Partial results:** a task with some failed/skipped steps still completes, and its result is a real synthesis (see below) of whatever succeeded — not silently dropped. `Synthesizer`'s provenance footer names every step and whether it completed, so "some sub-tasks didn't work" is visible in the response, not hidden. This was a deliberate choice over failing the whole task on any single step failure — a plan with 4 independent research steps where 1 fails shouldn't discard the other 3's work.

**Synthesis (`app/synthesis/synthesizer.py`):** a single-step plan's output *is* the result — no LLM call to "combine" one thing. A multi-step plan gets one extra LLM call (`Synthesizer._compose_body`) that integrates the step outputs into a coherent answer to the original goal, rather than the naive concatenation Phase 3 used as a placeholder. Every result — single- or multi-step — gets a deterministic (non-LLM) `## Sources` footer listing each step's id, agent, action, and whether it completed, so provenance never depends on the LLM remembering to mention it.

**Cancellation and background execution:** planning stays synchronous in `TaskManager.submit` (fast, and preserves the 422 contract), but execution is hard to cancel usefully if it's still running inside the original request — so `TaskManager.submit` hands the validated plan to `TaskRunner.start`, which schedules it via a plain `asyncio.create_task` and returns immediately (task status `EXECUTING` in the response). `TaskRunner` opens its **own** DB session (`get_session_factory`, not the request's `get_db_session`) since the request's session is closed by the time a background run does anything — reusing it would also violate the one-session-per-coroutine-group rule from Section 3. `ExecutionEngine.run` takes an optional `is_cancelled` callback, checked before each `parallel_groups` layer; once cancelled, every not-yet-run step is marked `SKIPPED` and the loop stops — a step already in flight is not interrupted mid-call (no cheap way to abort a live LLM request), so cancellation takes effect at the next layer boundary, not instantly. `POST /tasks/{id}/cancel` just flips the task's status to `CANCELLED` in the DB; `TaskRunner` discovers this the next time it checks, and `InvalidTaskStateError` (409) rejects cancelling a task that's already in a terminal state.

## 5. One Thing I Would Do Differently With More Time

**A durable job queue instead of `asyncio.create_task`.** Phase 4's background execution (`TaskRunner.start`, see Section 4) schedules a task's execution as a fire-and-forget coroutine on the app process's own event loop. That's enough to make cancellation and monitoring real, and it's honest about its own limits — but it has one gap I'd fix first with more time: if the app process crashes or restarts while a task is `executing`, that task is orphaned. Its row sits at `executing` forever; nothing re-drives it, and nothing marks it `failed` either. There's also no way to run more than one app instance, since each instance only knows about the background tasks it personally scheduled — an `executing` task's actual execution lives entirely in one process's memory, not in the database.

The fix is a proper job queue: instead of `asyncio.create_task`, a task ready for execution would be written to the DB as a pending job (a `SELECT ... FOR UPDATE SKIP LOCKED` claim, which Postgres already supports with no new infrastructure) that any worker process — including a fresh one after a restart — can pick up. That would also make horizontal scaling (multiple app instances) and a proper startup-time reconciliation pass ("resume or fail anything stuck `executing`") possible, neither of which the current design can do. I scoped it out for this assignment because it's a meaningfully bigger piece of infrastructure than the phase warranted, but it's the first thing I'd build next.
